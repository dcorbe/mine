DUPKEY30.DAT -- a synthetic duplicate-key file, built by the real engine.

WHY THIS EXISTS

Nothing MajorMUD ships can exercise a duplicate-permitting index: every
record-holding file has a unique key (crates/mbbs/tests/btrieve.rs's FILES
table shows duplicate-shaped `phys` deltas on WCCUSERS/WCCBANKS/WCCGANGS/
WCCITOWN, but none of those files can be re-created from scratch and none
holds records with colliding keys to walk). WCCUSERS key 2 is experience --
4 bytes at record offset 60, descending, duplicates permitted -- and every
newly created MajorMUD character has exp 0, so every character save collides
on it. This host could not write such an index (crates/mbbs/src/btrieve/
pages.rs:531) and no existing harness could prove an implementation, because
there was nothing on hand for the real engine to have built one out of.

DUPKEY30.DAT is that missing input: a 12-byte-record file with one 4-byte,
descending, duplicate-permitting key (WCCUSERS key 2's shape, minus the other
59+ fields), holding 30 records whose key values collide in groups of three
(`value = index / 3`, so keys 0..9 each own exactly 3 records).

REGENERATE IT

    sh tools/btrieve-oracle/build.sh
    cd tools/btrieve-oracle
    # Pick a name never used before in this Wine prefix -- see the file
    # header comment in btrvprobe.c: the Microkernel caches pages by path
    # and outlives its clients, so reusing a name serves stale pages.
    WINEPREFIX=$HOME/.btrieve-wine wine btrvprobe.exe create 'C:\btrieve\<unique>.DAT'
    WINEPREFIX=$HOME/.btrieve-wine wine btrvprobe.exe insert 'C:\btrieve\<unique>.DAT' 30
    WINEPREFIX=$HOME/.btrieve-wine wine btrvprobe.exe stat   'C:\btrieve\<unique>.DAT'
    WINEPREFIX=$HOME/.btrieve-wine wine btrvprobe.exe keys   'C:\btrieve\<unique>.DAT' 0
    WINEPREFIX=$HOME/.btrieve-wine wine btrvprobe.exe dump   'C:\btrieve\<unique>.DAT' 0
    cp "$HOME/.btrieve-wine/drive_c/btrieve/<unique>.DAT" tools/btrieve-oracle/fixtures/DUPKEY30.DAT

This copy was built as C:\btrieve\DUPK20.DAT (2026-08-08); the `stat` output
below is that run with the path line normalized to the fixture's name.

THE TWO MEASUREMENTS

1. Distinct key values. `keys` walks records via B_GET_FIRST/B_GET_NEXT, and
   for a duplicate-permitting key that operation visits every record in the
   chain (standard, documented Btrieve behaviour) -- so it prints 30 lines,
   not 10. All 30 inserts returned status 0 (OK), which is itself evidence
   duplicates are permitted: if they were not, the 2nd and 3rd insert of
   each group of three would have come back status 5 ("duplicate key
   value"), and none did. `sort DUPKEY30-keys.txt | uniq -c` collapses the
   30 lines to exactly 10 distinct values, each appearing exactly 3 times
   consecutively -- 30 records over 10 distinct key values, confirmed, just
   not as a literal 10-line `keys` output. Reading raw index-page bytes to
   count physical index *entries* directly (rather than inferring from a
   record-level walk) would need a page-level reader this rig does not have;
   out of scope for Task 6/7.

2. Physical record length. `stat`'s `reclen` field reads 12 on this file
   both before any records existed (Task 6) and after all 30 were inserted
   (below) -- NOT 20. `dump`'s `dlen` also reads 12 for every record. Real
   Btrieve's own STAT reply reports the DECLARED logical length; it does not
   surface whatever the engine stores physically on the data page. So the
   design's "20, not 12" prediction cannot be confirmed or refuted through
   `stat` or `dump` as built here -- both instruments are blind to it.

   Reading the raw page bytes directly (a one-off Python script against this
   file, not a btrvprobe command, and not committed) settles it anyway: the
   three records sharing key value 9 sit at byte offsets 4192, 4214 and 4236
   in page 8 -- a stride of exactly 22 bytes per record, not the declared 12.
   A throwaway comparison file, built the same way but with the duplicates
   bit cleared (unique key, same reclen 12, same pagesize), showed a stride
   of 14 bytes instead. The delta -- 22 - 14 = 8 -- is exactly the
   [prev][next] chain pair `pages.rs:531` predicts, sitting on top of a
   2-byte per-record slot header that both files carry regardless of
   duplicates (14 = 12 + 2; 22 = 12 + 2 + 8) and that has nothing to do with
   this question. So the underlying "12 logical + 8-byte chain pair" claim
   is confirmed at the byte level, against a file the real engine wrote --
   crates/mbbs/tests/btrieve.rs's existing `phys` column already assumes
   exactly this delta for WCCUSERS/WCCBANKS/WCCGANGS/WCCITOWN (1998->2006,
   72->80, 253->261, 65->73, all +8) -- but neither `stat` nor `dump`
   reports it, so this fixture cannot prove it by itself; the raw bytes can.
